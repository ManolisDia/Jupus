# 2026-08-24-002 — shared sqlite3.Connection now reachable from multiple worker threads, unverified for thread-safety

## Context
Not a symptom — flagged by the independent Phase 6 merge review (`docs/workflow.md`'s
pre-merge process) while sanity-checking `backend/dispatcher.py`'s `asyncio.to_thread` fix
(see the fix that made `dispatcher.process_supervisor_call` run `GRAPH.invoke` off the event
loop, so real blocking Claude calls stop freezing `/bridge`'s VAD read loop).

## The implication
`backend/db/repositories/__init__.py` shares a single `sqlite3.Connection` across all
repositories, created once at startup with `check_same_thread=False`. Before the
`asyncio.to_thread` fix, the whole app only ever ran one Python thread at a time — real
concurrent use of that connection across two different in-flight calls was never actually
possible, `check_same_thread=False` or not. After the fix, two different calls' `GRAPH.invoke`
chains can genuinely run on two different OS worker threads at the same moment (each call's own
`asyncio.Lock` in `dispatcher.LOCKS` only serializes turns *within* that one `call_id`, not
across different calls), so the shared connection can now actually be hit concurrently for real.

Python's `sqlite3` module only guarantees this is safe if the underlying SQLite build was
compiled in serialized-threading mode — usually the default, but not verified anywhere in this
codebase or its docs.

## Current assessment
Low practical risk for this project: a local take-home with effectively one caller at a time
during manual/demo testing. Not treated as a merge blocker for Phase 6. Flagging as a known,
unverified assumption for whoever later tests genuinely concurrent/multi-caller scenarios (e.g.
Phase 7's live demo overlapping with a second test call, or any future multi-tenant use).

## Possible fix directions (not yet needed)
1. Confirm the local SQLite build's threading mode (`sqlite3.threadsafety` at runtime, or the
   linked library's `SQLITE_THREADSAFE` compile flag) and document it explicitly rather than
   assuming.
2. If genuine multi-caller concurrency is ever a real requirement, give each repository its own
   connection (or a small connection pool) instead of one shared instance — the repository
   pattern in `docs/architecture.md` already isolates callers from the connection object, so this
   would be a localized change in `backend/db/repositories/connection.py`, not a wider refactor.
