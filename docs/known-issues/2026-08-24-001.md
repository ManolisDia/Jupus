# 2026-08-24-001 — Real LLM judge never flags the 4 hand-seeded error-class demo calls

## Symptom
Ran `python -m eval.run_eval --label live-verify-phase6` for real (real `ANTHROPIC_API_KEY`,
no mocking) against the 8 rows from `backend/db/seed_demo_calls.py`. Only `demo-escalated-1` got
any `call_error_flags` rows. The 4 calls purpose-built to exhibit a specific error class
(`demo-repetition-1`, `demo-tool-failure-1`, `demo-premature-escalation-1`,
`demo-unconfirmed-action-1`) got zero flags each — the exact opposite of what
`phase-6b-error-taxonomy.md`'s DoD item ("each of the 4 error-class-specific seeded calls is
confirmed flagged with its intended class") expects.

## Root cause
`classify_call_errors` (`backend/supervisor/tools.py`) builds its judge prompt from
`call_row["outcome"]`, `call_row["escalation_reason"]`, and `trace` — explicitly **not** the flat
`transcript_json` (see the function's own docstring: "using its outcome/escalation_reason plus its
full trace... as evidence"). `seed_demo_calls.py` (per `phase-6a-observability.md`'s own spec)
inserts rows directly into `calls` with a hand-authored `transcript_json`, "bypassing the live
pipeline entirely" — which means no `trace_events` rows are ever written for any seeded call. The
judge is therefore given an empty trace and only outcome/escalation_reason for all 8 rows; it has
no evidence at all for the 4 calls whose defining characteristic (repeated turns, a surfaced tool
failure, a premature escalation, an unconfirmed action) only exists in `transcript_json`, which it
never sees. `demo-escalated-1` incidentally still got flagged because "escalated with an empty
trace" is itself suspicious-looking evidence to the judge — not because the judge read the
transcript.

`eval/tests/test_seed_demo_calls.py::test_seed_includes_one_example_per_error_class` only checks
that `transcript_json` is structurally shaped correctly per its own docstring ("doesn't prove the
LLM will classify it correctly, only that the fixture is well-formed") — so this mismatch between
what the seed produces (transcript-only evidence) and what the real judge reads (trace-only
evidence) was never exercised by the mocked test suite, only surfaced once real API keys made a
real classification pass possible.

## What was ruled out
- Not a credentials/placeholder-key issue — `run_eval.py` ran for real and returned real
  classifications; it just correctly found no trace-based evidence to flag on.
- Not a bug in `classify_call_errors` itself, `run_eval.py`'s call selection, or `call_error_flags`
  writing — `eval/tests/test_run_eval_integration.py` already proves the harness attributes flags
  to the right `call_id` when the classifier does return a match.

## Current best hypothesis / options not yet chosen between
1. Extend `seed_demo_calls.py` to also hand-author plausible `trace_events` rows per error-class
   call (mirrors the flaw the transcript already encodes) so the real judge has the same evidence
   a live pipeline call would produce.
2. Extend `classify_call_errors`'s prompt to also take `transcript_json` as evidence, not just
   trace — a bigger design change since the function's docstring treats trace-only as deliberate.
3. Accept this as a documented limitation of hand-seeded demo data specifically, and treat
   `test_scenarios.py`'s 6 real-pipeline scenarios (which do produce real trace_events) as the
   actual proof that live-call classification works, leaving the seeded-demo DoD item permanently
   unchecked with this note rather than forcing seed data to fake trace evidence.

No workaround applied yet — flagging for the user to pick a direction before `eval/error_classes.py`
or `seed_demo_calls.py` change under this issue.
