# `eval/replay_scenarios.py` intermittently loses the background statute-search task entirely

**Symptom**: `dispatcher._search_statutes_in_background` (Phase 8's background statute-grounding
task, spawned via `dispatcher.STATUTE_SEARCHES`) sometimes never completes when driven through
`eval/replay_scenarios.py`'s S7a/S7b scenarios — its `search_statute_candidates` tool call records a
`tool_call_start` trace event and then nothing else: no `tool_call_end`, no `ground_statute_citation`
call, no error, no exception surfaced anywhere. The task appears to simply stop making progress.

**Confirmed NOT a correctness bug in the feature itself**: driving the exact same 8 utterances
through `dispatcher.process_supervisor_call` directly in an isolated script (not via
`replay_scenarios.py`), then explicitly `await`ing `dispatcher.STATUTE_SEARCHES[call_id]`, works
reliably every time — full `search_statute_candidates` → `ground_statute_citation` round trip
completes with a real, correct result (confirmed for both Sonnet and Haiku, matching citations
selected by both). The bug is specific to something about `replay_scenarios.py`'s execution shape.

**Partial fix applied, not a full fix**: `eval/replay_scenarios.py`'s `_replay_one` now explicitly
awaits `dispatcher.STATUTE_SEARCHES.get(call_id)` after its scripted utterance loop finishes (Phase
13, mirroring `backend/tests/test_scenarios.py`'s `_await_statute_search` helper) — this is
correct and necessary, but not sufficient: in the full S7a/S7b run (with `extract_datetime`,
`select_offered_slot`, and `book_consultation` calls all still running as real, slow, live API calls
immediately after research completes), the background task still sometimes never reaches a state
where this await can succeed — by the time the script gets there, the task is gone from
`STATUTE_SEARCHES` in a way that suggests either (a) it was popped by an intervening
`_reconcile_statute_search` call from a later turn despite never actually finishing, or (b) the
underlying `asyncio.to_thread` work item never got scheduled at all during the full script's turn
sequence. Not root-caused — ruled out an exception being silently swallowed (nothing in `except
LLMCallFailed` would explain a missing `tool_call_end` on the deterministic `search_statute_candidates`
call, which isn't LLM-backed at all).

**Workaround used to unblock the Phase 13 Haiku-vs-Sonnet comparison for `ground_statute_citation`**:
bypassed `replay_scenarios.py` entirely — drove the scenario's utterances through
`dispatcher.process_supervisor_call` directly in a standalone script, per the "confirmed NOT a
correctness bug" section above. Real numbers obtained this way: Sonnet 4090ms / Haiku 1367ms for the
same utterance, both selecting the identical statute id.

**Next steps for whoever picks this up**: instrument `_search_statutes_in_background` with
before/after timestamps logged directly (not just via `trace_events`, which this bug shows can go
missing) to see whether the task is created but never scheduled, or scheduled and silently
cancelled. Also worth checking whether `asyncio.run()`'s default executor interacts badly with the
number of concurrent `asyncio.to_thread` calls in flight during the tail of a scenario replay
(several real, slow API calls queued back-to-back) — Phase 12's stress-test work
(`docs/phases/phase-12-concurrency-stress-test.md`) already found the default executor's cap
relevant under load; this may be a related, smaller-scale version of the same class of issue.
