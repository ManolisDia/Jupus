# Scenario tests silently make real, paid Anthropic API calls on turn 1

**Symptom**: `backend/tests/test_scenarios.py` and `backend/tests/test_capture_fast.py`'s
`test_dispatcher_only_spawns_background_verification_on_real_advance` are meant to be fully mocked
(no live API calls), per the repo-wide pytest contract (CLAUDE.md: "run unit tests" via `pytest` is
documented as fast/mocked, distinct from `eval/replay_scenarios.py`'s explicitly-live runs). In
practice, several of these tests silently make a real, unmocked call to `classify_practice_area` on
their very first turn, hitting the live Anthropic API and incurring real (small) cost on every
`pytest` run.

**Root cause, confirmed**: `dispatcher.process_supervisor_call` chains straight from `node_greeting`
into the next node within the same dispatch when the call starts from the `"greeting"` stage (see
its own comment: "node_greeting is a silent, content-blind stub... chain straight into the next node
now, within the same dispatch"). Concretely: turn 1's first `GRAPH.invoke` runs `node_greeting`
(bumps stage to `"routing"`, no LLM call), and since `stage_before == "greeting"` and the new stage
isn't `ended`/`escalation`, `process_supervisor_call` immediately invokes the graph a **second** time
with the same utterance — which now routes to `node_routing`, calling `classify_practice_area` for
real. Every affected test's `with patch("backend.supervisor.tools.classify_practice_area", ...)`
block is written around a **later** turn, on the assumption that turn 1 only reaches
`node_greeting`/stops at `"routing"` — it doesn't; the classify call already happens inside turn 1,
unmocked.

**Confirmed via**: patching `backend.supervisor.llm_utils._client.messages.create` to raise
unconditionally and re-running the affected test files — every failure traced back to `node_routing`
calling the real `classify_practice_area` on turn 1, in tests whose classification mock is scoped
to turn 2 onward. Verified this is **pre-existing**, not introduced by Phase 13's tool-merging work
(`docs/phases/phase-13-latency-reduction.md`): identical failures reproduce on the commit before that
phase's changes. Explains why `test_scenarios.py` alone takes ~15-20s to run — that's real per-call
API latency, not test overhead.

**Affected tests** (as of this writing): `test_scenario_s2_happy_path_booking`,
`test_scenario_s3_slot_conflict_booking`, `test_scenario_s4_low_confidence_capture`,
`test_scenario_s7_case_research_with_citation`, `test_scenario_s7_case_research_no_citation`
(all in `test_scenarios.py`), and `test_dispatcher_only_spawns_background_verification_on_real_advance`
(`test_capture_fast.py`). Each of these currently passes — the real API response happens to be
plausible enough not to trip any assertion — but the underlying leak is real.

**Not fixed here**: fixing it means either (a) wrapping each affected test's turn-1 call in its own
`classify_practice_area` mock, or (b) restructuring `_turn`/test helpers to patch it session-wide by
default. Both are straightforward but out of scope for Phase 13 (latency reduction), which only
touched `node_capture`'s extraction path. Whoever picks this up next: start from the diagnostic
technique above (patch `_client.messages.create` to raise, re-run, read the traceback for which node
called it) rather than re-deriving this from scratch.
