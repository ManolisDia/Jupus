# 2026-08-22-001 — Interrupted realtime response silently drops the `ask_supervisor` tool call

## Symptom
During a live Phase 5 manual test (multi-area escalation), the agent said something that
sounded like a checking/filler phrase, then went silent instead of finishing its turn. No
`ask_supervisor` message ever reached `/bridge` for that utterance — `backend.log` shows zero
Claude API calls and zero `POST` activity after the greeting turn, confirming the backend/graph
was never invoked. On the caller's next utterance ("hello"), the model treated it as a brand new
turn and improvised an unrelated line ("hi what do you need again?") instead of picking up the
dropped tool call or re-asking.

## What was ruled out
- Not a `node_routing`/escalation graph bug — the graph was never invoked at all for the dropped
  turn, so `multiple_areas` classification, the retry-vs-escalate branch, etc. are not implicated.
  A separate successful run in the same session (`call_id=3f8c7364-...`) already confirmed
  `classify_practice_area` → `multiple_areas` → immediate escalation with no retry loop works
  correctly end-to-end when the tool call actually fires.
- Not the deferred-delivery/staleness mechanism (`dispatcher.deliver_or_defer`/`drain_deferred`) —
  no reply was ever generated to defer or drop; the turn never produced a supervisor call in the
  first place.

## Current best hypothesis
Race between response generation and interruption. `client/app.js`'s `sendSessionUpdate`
(`turn_detection: {type: "semantic_vad", eagerness: "low", create_response: true,
interrupt_response: true}`) means any further detected speech (ambient noise, a breath, mic
self-noise) cancels an in-flight response before it completes. `client/app.js`'s data-channel
handler only ever sends `ask_supervisor` to the backend on
`response.function_call_arguments.done` (`client/app.js:221-232`) — there is no handler for
`response.cancelled`/`response.done` with no function call present. If the response is cancelled
mid-generation, after the model has started speaking but before it finishes emitting the
function-call arguments, the turn is silently lost: nothing retries it, nothing tells the model
it was cut off mid-tool-call.

This is the same root cause category as `docs/fixes/2026-08-21-001.md` (semantic_vad
over-triggering on ambient noise / self-interruption), which fixed a *different* symptom (dropped
audio) with `near_field` noise reduction + lower eagerness. That fix reduces but evidently does
not eliminate spurious interruptions, and this phase is the first one where an interruption can
also cost a tool call, not just audio continuity — so the same underlying trigger now has a worse
failure mode (a fully dropped turn / silent instruction violation) rather than a cosmetic one.

## Failed workarounds
- Tried option 1 below: a `response.done` handler that re-sent a bare `response.create` when a
  response ended `cancelled`/`incomplete` with no completed function call, guarded by a
  `responseActive` flag to skip retrying when the caller's own next utterance had already gotten
  its own auto-created response. Reverted — `responseActive` is a single shared boolean, not
  scoped per response ID. Event ordering between the cancelled response's `response.done` and the
  interrupting response's `response.created` isn't guaranteed; when they arrive out of the assumed
  order, the guard clears itself incorrectly and the retry fires `response.create` while a
  different response is genuinely still active, reproducing a new, worse symptom: the Realtime API
  hard-rejects the collision ("Conversation already has an active response in progress") and the
  whole session errors out and tears down — confirmed live, twice, after the "fix" shipped. See
  `docs/DECISIONS.md`'s `interrupt_response` entry for the full history.
- Also tried disabling `interrupt_response` entirely, reasoning the Phase 5 async flow doesn't
  need mid-response interruption. Reverted even faster: without interruption, a genuinely
  overlapping caller utterance still gets its own auto-created response, but nothing cancels the
  old one to make room — the exact same collision error, just from the opposite direction.

Current position: `interrupt_response: true`, no client-side retry-on-cancel at all. A spurious
cancellation still silently drops that turn (the original symptom), but that's judged the smaller
failure compared to a retry mechanism that's shown, twice, that it can crash the whole call instead
— and this session couldn't get a client-side event-stream capture reliable enough (no direct way
to observe the user's actual live browser session) to trust a more careful per-response-ID fix
without live-testing it into a third regression.

## Update 2026-08-24 — confirmed occurring naturally, not just from the reverted retry code
While manually testing Phase 6a's deferred-`wait_ms` DoD item (talk continuously, with no gap,
immediately after finishing an utterance — deliberately trying to overlap with an in-flight
response so its reply gets deferred rather than delivered), the client surfaced the exact
collision error directly from the API: `"Conversation already has an active response in
progress... Wait until the response is finished before creating a new one."` No client-side
retry-on-cancel code is present on this branch (reverted per the section above) — this fired
straight from `interrupt_response`'s own cancel/create race, confirming the race isn't only
reachable through the retry mechanism that was reverted, it's reachable from normal (if
aggressive) caller speech patterns. Notably, "talk again immediately with no gap" is exactly the
technique needed to manually verify the deferred-reply DoD item, so this issue may block reliably
reproducing that check through the real browser client until fixed.

## Possible fix directions (not yet implemented)
1. A correctly-scoped version of the retry: track the active response's own ID (from
   `response.created`'s and `response.done`'s `response.id`), not a single shared boolean, and
   only retry if no *other* response has claimed the slot since. Needs to be verified against a
   real captured event stream (browser console / network inspector on the actual test session)
   before shipping again, not reasoned about from trace logs after the fact.
2. Further tune interruption sensitivity (eagerness/noise reduction) if the underlying dropped-turn
   symptom (not the crash) keeps recurring on quiet input, similar to the 2026-08-21-001 fix.
