# 2026-08-22-001 — Interrupted realtime response silently drops the `ask_supervisor` tool call

## Symptom
During a live Phase 5 manual test (multi-area escalation), the agent said something that
sounded like a checking/filler phrase, then went silent instead of finishing its turn. No
`ask_supervisor` message ever reached `/bridge` for that utterance — `backend.log` shows zero
Claude API calls and zero `POST` activity after the greeting turn, confirming the backend/graph
was never invoked. On the caller's next utterance ("hello"), the model treated it as a brand new
turn and improvised an unrelated line ("hi what do you need again?") instead of picking up the
dropped tool call or re-asking.

## What was ruled out
- Not a `node_routing`/escalation graph bug — the graph was never invoked at all for the dropped
  turn, so `multiple_areas` classification, the retry-vs-escalate branch, etc. are not implicated.
  A separate successful run in the same session (`call_id=3f8c7364-...`) already confirmed
  `classify_practice_area` → `multiple_areas` → immediate escalation with no retry loop works
  correctly end-to-end when the tool call actually fires.
- Not the deferred-delivery/staleness mechanism (`dispatcher.deliver_or_defer`/`drain_deferred`) —
  no reply was ever generated to defer or drop; the turn never produced a supervisor call in the
  first place.

## Current best hypothesis
Race between response generation and interruption. `client/app.js`'s `sendSessionUpdate`
(`turn_detection: {type: "semantic_vad", eagerness: "low", create_response: true,
interrupt_response: true}`) means any further detected speech (ambient noise, a breath, mic
self-noise) cancels an in-flight response before it completes. `client/app.js`'s data-channel
handler only ever sends `ask_supervisor` to the backend on
`response.function_call_arguments.done` (`client/app.js:221-232`) — there is no handler for
`response.cancelled`/`response.done` with no function call present. If the response is cancelled
mid-generation, after the model has started speaking but before it finishes emitting the
function-call arguments, the turn is silently lost: nothing retries it, nothing tells the model
it was cut off mid-tool-call.

This is the same root cause category as `docs/fixes/2026-08-21-001.md` (semantic_vad
over-triggering on ambient noise / self-interruption), which fixed a *different* symptom (dropped
audio) with `near_field` noise reduction + lower eagerness. That fix reduces but evidently does
not eliminate spurious interruptions, and this phase is the first one where an interruption can
also cost a tool call, not just audio continuity — so the same underlying trigger now has a worse
failure mode (a fully dropped turn / silent instruction violation) rather than a cosmetic one.

## Failed workarounds
None attempted yet — this is a fresh finding from live Phase 5 testing, not yet fixed.

## Possible fix directions (not yet implemented)
1. Client-side robustness: handle `response.cancelled` (or `response.done` with no
   `function_call_arguments.done` having fired) in `client/app.js`'s data-channel handler —
   either re-send `response.create` to prompt the model to retry, or otherwise recover rather
   than silently dropping the turn.
2. Further tune interruption sensitivity (eagerness/noise reduction) if this keeps recurring on
   quiet input, similar to the 2026-08-21-001 fix.
