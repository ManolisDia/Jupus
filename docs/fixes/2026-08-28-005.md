# 2026-08-28-005 — the caller's answer credited to a field they were never asked about: `last_asked_field` was re-derived by scanning statuses instead of stated by the reply that asked

## Symptom
Live call, immediately after `docs/fixes/2026-08-28-004.md` landed. The retry loop was gone, but
the caller was made to repeat themselves twice more:

- **Email asked for twice.** Asked to spell out their email (#33), the caller did — "Yeah, it's
  M-A-N-O-S at G-M-A-I-L dot C-O-M." That utterance was fed to `confirm_field_answer` as a yes/no
  about their **name** (#42), which "confirmed" it, and the agent then asked for the email address
  all over again (#45).
- **Phone confirmed back twice.** The agent read the phone number back (#72), the caller said
  "Yes." — and that yes was applied to **email** (#81), a field whose confirm-back had never been
  spoken. With phone still unconfirmed, the agent read the phone number back a second time (#89),
  needing a second "Yes." (#98).

## Root cause
One line, firing twice. `_sync_last_asked_field` (`backend/supervisor/graph.py`) reconstructed
`last_asked_field` after a `_fallback_to_real_capture` by scanning `caller_profile` for the first
`pending_confirm` field in `FIELD_PRIORITY` order, falling back to the first `missing` one:

```python
pending = next((f for f in FIELD_PRIORITY if profile[f]["status"] == "pending_confirm"), None)
if pending:
    return pending
```

`last_asked_field` means "the field the caller's NEXT utterance is presumed to answer"
(`state.py`), so it must be the field the reply just spoken actually asked about. A status scan is
only the same thing when the field just spoken about happens to be the first one in
`FIELD_PRIORITY` order holding that status — and under Phase 7 it routinely isn't, because
background verification leaves *earlier* fields sitting in `pending_confirm` with their
confirm-backs deliberately unspoken, batched for the drain phase. That is the normal state of a
call, not an edge case:

- **#33** — node_capture re-asked for the **email** (`_deny_and_reprompt`), but `name` was
  `pending_confirm` from a 0.6 background check, so the scan returned `name`. The caller's next
  utterance, spelling out their email, was credited to `name`.
- **#72** — node_capture spoke **phone**'s confirm-back, but `email` had been left
  `pending_confirm` by the previous turn, so the scan returned `email`. The caller's "Yes" was
  credited to `email`.

The docstring claimed it re-derived the field "the same way node_capture's own bottom logic
would." It didn't: node_capture has six paths that speak a field-specific question and each one
knows exactly which field it is about, but it discarded that and let the caller re-derive it from
statuses. The information was never missing — it was thrown away and then guessed at.

This is also the root cause of `docs/known-issues/2026-08-25-001.md`, open since 2026-08-25 and
now closed (moved to `docs/fixes/2026-08-28-006.md`). That call followed the identical chain: a
low-confidence email was re-asked, the scan returned `name` (pending_confirm at 0.7 from a
background check), and every subsequent turn then ran `confirm_field_answer` against `name` while
the caller spelled out an email — the entry's central unexplained observation. Its own leading
hypothesis was that field selection should *guess better*, by inspecting the utterance for "@"/
"at"/"dot". The real answer is that it should not be guessing at all.

## Fix
`node_capture` now returns `last_asked_field` itself on every path that speaks a question about a
specific field: `_deny_and_reprompt`'s re-ask and its escalation, the `needs_clarification`
repeat, a freshly extracted field's confirm-back, the drain phase's next-pending confirm-back, and
the plain "Thanks — and what's your X?". `_sync_last_asked_field` is deleted;
`_fallback_to_real_capture` uses `result.setdefault("last_asked_field", state["last_asked_field"])`
so the two paths that *don't* speak about a field — entering research, and the upstream-failure
fallback — leave the outstanding question exactly as it was.

Nothing about the inbound guard changed: `allowed_pending_field` (`docs/fixes/2026-08-24-009.md`)
still restricts which field an utterance may be treated as confirming. That guard was always
correct and was being fed a wrong `last_asked_field` — the two fixes are the inbound and outbound
halves of the same invariant, which is now true in both directions: **a field is only ever
confirmed against an utterance that followed its own spoken question.**

## Verification
`pytest backend/tests eval/tests` — 419 pass (416 before, +3 new), plus
`scripts/check_architecture.py`. The three new tests in `test_capture_fast.py` cover the re-ask
case, the confirm-back case, and the follow-on turn where "Yes." must resolve phone and not repeat
it; an existing sibling test (`test_gate_fallback_does_not_confirm_an_unrelated_earlier_pending_
field`) gained the `last_asked_field` assertion it had been missing, and fails without this fix
too. All four were confirmed to fail against the old derivation, reproducing the live trace
exactly — `confirm_field_answer('Yes.', 'email', 'manos@gmail.com')` where
`confirm_field_answer('Yes.', 'phone', '07577670101')` was expected, i.e. trace #81 verbatim.
Not yet re-verified on a live call.

## Noted, not fixed
`node_capture`'s `needs_clarification` branch repeats the previous question without incrementing
`attempts`, so it has no escalation ceiling of its own. It is now self-consistent (it re-asks the
field it was actually about, and the caller's answer is credited to that same field), so it can no
longer be driven by a misattribution the way `docs/known-issues/2026-08-25-001.md`'s loop was —
but a caller who keeps answering a confirm-back ambiguously would still cycle. Not observed in any
captured call; flagged rather than changed, since making it count attempts risks escalating a
legitimate "sorry, what?" exchange.
