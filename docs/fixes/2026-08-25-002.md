# `confirm_field_answer`'s multi-second retry tail — unbounded `corrected_value` verbosity hit `max_tokens=512` mid-generation

**Symptom**: Phase 11 trace data showed `confirm_field_answer` with a 2035ms median but a 10229ms
max — a ~5x outlier — while `confirm_booking_answer` (a structurally similar tool, boolean-only
schema) showed no comparable outlier and zero retry events. Scoped in Phase 13
(`docs/phases/phase-13-latency-reduction.md`, Decision 4) as "root-cause the retry tail, don't just
tolerate it."

**Root cause, confirmed via a real live call's trace_events** (`call_id=56e57e0f-4f2c-45e0-821f-207ddfae774a`,
2026-08-25): a caller repeatedly, confusingly re-spelled an email ("M, A, N, O, S, at, G, M, A." →
"M-A-N-O-S at G-M-A-I-L dot C-O-M." → ...). Each `confirm_field_answer` call's `llm_usage` event
showed wildly variable `output_tokens` for what should be a compact 3-field JSON object
(`confirmed`, `corrected_value`, `needs_clarification`): 201, then 351, then a call that failed
outright, then 274, 178, 30. The failed call's two attempts both took ~7.5s and both errored with
`json.JSONDecodeError: Unterminated string starting at...` — the model's `corrected_value` output
grew long enough (evidently attempting to reason about or restate the caller's full spelled-out
utterance) to exceed `call_claude_json`'s `max_tokens=512` mid-generation, producing truncated,
invalid JSON. `call_claude_tool`'s existing retry-once behavior (`llm_utils.py`) then re-ran the
same call, which failed the same way a second time, before finally falling back to a generic
"could you say that again?" reply. Two ~7.5s attempts plus the 0.5s retry backoff is exactly
where a ~10s+ observed max comes from.

**Why `confirm_booking_answer` didn't show this**: its schema (`accepted`, `needs_clarification`)
has no free-text field at all — there's nothing for a confused generation to balloon into. This
confirms the fix belongs on `CONFIRM_FIELD_ANSWER_PROMPT` specifically, not `call_claude_tool`'s
retry/timeout machinery generally.

**Fix**: `CONFIRM_FIELD_ANSWER_PROMPT` (`backend/supervisor/prompts.py`) now explicitly constrains
`corrected_value` to "nothing more than the corrected value itself — never an explanation, never
your reasoning about what the caller might have meant, and never a restatement of their full
spelled-out utterance," even across repeated respelling. Deliberately **not** fixed by raising
`max_tokens` instead — that would let the wasteful, verbose generation succeed rather than fail,
masking the symptom without making the call any faster (a 351-token generation is already most of
the way to this outlier's cost; letting a 500+ token one through doesn't help median or tail
latency, it just stops it from erroring).

**Not yet re-verified against a real garbled-respelling call** (would need deliberately reproducing
the same confusing caller behavior live) — the fix is grounded in the actual mechanism found in the
trace, but hasn't been re-triggered live post-fix. If this resurfaces, check `llm_usage.output_tokens`
for `confirm_field_answer` first; a return to 300+ token outputs means the prompt constraint isn't
holding and needs strengthening further, not that `max_tokens` needs raising.
