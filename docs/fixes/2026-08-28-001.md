# Live transcript showed one spoken word as four bubbles, plus a stranded "…" per repeat

**Symptom**: A caller said "Hello" once and the client's live transcript rendered:

```
…
Hello
…
Hello.
…
Hello.
Hello.
Hi there, thanks for calling. What can I help you with today?
```

Reported from a real local call, 2026-08-28. The DB transcript for the same class of call was
correct (one entry per utterance), which localised it to the browser, not the supervisor.

**Root cause**: `registerTranscriptHandlers` (`client/livekit-transport.js`) called
`appendTranscriptTurn` on **every** text stream arriving on the `lk.transcription` topic.
livekit-agents publishes a single segment as a *series* of streams sharing an `lk.segment_id`:
interim results tagged `lk.transcription_final: "false"` as ASR refines its guess, then a closing
one tagged `"true"` (see the installed `livekit/agents/voice/room_io/_output.py`, which sets
`"false"` at the writer-creation site and `"true"` in `_flush_task`). Each stream carries the whole
segment, not a delta — so four progressively-refined renderings of "Hello" became four bubbles.

The stranded `…` bubbles came from the same line. `showThinkingBubble()` also ran per interim, and
it *assigns* `thinkingBubbleEl` on each call — so `removeThinkingBubble()` only ever removed the
last one, leaving the earlier ones on screen for the rest of the call.

**Fix**: bubbles are keyed by `lk.segment_id` in a `transcriptBubbles` map and updated in place
(`upsertTranscriptTurn`, `client/app.js`), so a turn refines live instead of multiplying. The `…`
is now raised only when `lk.transcription_final !== "false"`. Both attribute names were checked
against `livekit/agents/types.py` (`ATTRIBUTE_TRANSCRIPTION_SEGMENT_ID`,
`ATTRIBUTE_TRANSCRIPTION_FINAL`) rather than assumed; a stream missing either degrades to the old
append-every-stream behaviour rather than dropping the transcript, since a missing transcript must
never be able to break the call.

**Note**: the map is cleared in `resetLiveUi()`. If this resurfaces, check first whether the SDK
still sets `lk.segment_id` — without it the code deliberately falls back to appending, which looks
exactly like the original bug.
