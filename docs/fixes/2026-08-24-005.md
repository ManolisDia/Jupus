# 2026-08-24-005 — Background field verification's urgent-reask signal could never fire correctly, misattributing a later utterance to a stale failed field

## Symptom
Found by an independent DoD review of the `phase-7-optimistic-capture` branch before merge, and confirmed against real live-call data already sitting in `backend/db/calendar.db` (call `f6ecbcc2-16bd-4189-a0b5-a5ce4306881d`): a caller's answer to the routing follow-up question got resubmitted (an apparent Realtime duplicate-submission artifact, unrelated to this bug) and was accepted by `node_capture_fast`'s gate as an answer to "what's your name?". The real background extraction for `name` correctly failed (confidence 0) several turns later — but nothing re-asked for it. Instead, once the drain phase's "first missing field" logic reached `name`, it silently re-extracted it from whatever utterance happened to be current at that point, which only produced the right value by coincidence (the caller happened to be saying their name again for an unrelated reason).

## Root cause
`dispatcher._reconcile_field_verifications` only flagged a background failure as urgent when `field == state.get("last_asked_field")`:

```python
elif field == state.get("last_asked_field"):
    state["verification_failed_field"] = field
```

This condition can essentially never be true. A field only gets a background verification task once `node_capture_fast` has already advanced `last_asked_field` *past* it — the task is spawned in the exact same return that produces the next field's question (`backend/supervisor/graph.py`'s `node_capture_fast`, the `background_verify_field` signal). So by the time that task can possibly have resolved, `last_asked_field` is always already pointing at a *later* field, never the one being checked. The urgent-reask mechanism was non-functional from the moment it was written, not just stale in an edge case — the independent review's live evidence just happened to surface it.

Once a field's background check failed silently (no explicit signal, `status` just stuck at `"missing"`), the only place it could ever get noticed was `node_capture`'s ordinary "first missing field" lookup, which unconditionally treats whatever utterance is currently in the transcript as that field's fresh answer — with no awareness that the utterance was actually answering something else entirely. A second, related gap: `node_capture` (registered as the `"capture_confirm"` graph node) has no concept of background verification failures at all, so the exact same misattribution could also happen if a failure surfaced *after* the confirm/drain phase had already started.

## Fix
1. `_reconcile_field_verifications` now flags a failure regardless of whether it matches the current `last_asked_field` — deterministic tie-break (earliest `FIELD_PRIORITY` position) if more than one resolves to failure in the same reconcile pass.
2. `node_capture_fast` and a new `node_capture_confirm` wrapper (previously `"capture_confirm"` pointed straight at unwrapped `node_capture`) both check for a pending failure signal *before* doing anything else, via a shared `_delayed_failure_reask` helper: it interrupts explicitly — "Sorry, I need to double check something — what's your X again?" — and deliberately does **not** process the current turn's utterance as an answer to anything. The caller repeats whatever they just said too, once things are back on track. `last_asked_field` moves to the failed field (and `capture_phase` force-resets to `"fast"` if triggered from the confirm phase) so the next utterance is correctly attributed.
3. `_next_fast_field` (the "what's next" sequencer) is now profile-aware rather than purely positional — after resuming from an interrupt, it correctly skips any field that was already resolved while the interrupt was being handled, instead of blindly re-asking the next `FIELD_PRIORITY` position regardless of its real status.

Regression tests added in `backend/tests/test_capture_fast.py`: a field failing after the fast pass has moved two fields ahead is caught and interrupts correctly without touching the current utterance or corrupting the failed field's stored value; the confirm phase's identical guard is exercised the same way; `_next_fast_field` is tested directly for the resume-skips-already-resolved-fields case.

## Known residual limitation, accepted rather than engineered around
A background check that is still genuinely in-flight (neither succeeded nor failed) by the time the confirm/drain phase begins is not explicitly awaited anywhere — `docs/phases/phase-7-optimistic-capture.md`'s original design called for the confirm phase to block on this, but doing so turned out to be unreachable dead code in practice (the last field is always processed live, never via background, so there was never actually a task left to await at that transition point). This fix closes the *failure* case, which is the one with real evidence of occurring; the *still-running* case would require a field's background Claude call to take longer than the caller needs to answer every subsequent field plus at least one drain turn combined — judged pathological enough in practice not to warrant blocking-wait infrastructure for it. Documented here rather than silently left unmentioned.
