# 2026-08-24-011 — hosted admin panel loaded with an empty calls list

## Symptom
`/admin?access_token=<token>` on the live Railway deployment rendered the page shell (header,
nav, empty "Select a call on the left" state) but the calls list was empty, even though
`curl https://.../api/calls` (ungated, outside `/admin`) confirmed the call was actually logged.
Browser console showed a 401 on page load.

## Root cause
`admin_access_gate` (`backend/app.py`) checked only `request.query_params.get("access_token")`.
The link a person is given (`/admin?access_token=...`) carries the token, but the browser's own
follow-up requests for that page's static assets (`/admin/app.js`, etc.) are plain same-origin
`GET`s with no query string at all — the middleware 401'd every one of them, so `admin/app.js`
never ran and never populated the calls list, despite `/api/calls` itself working fine (it isn't
gated, per the phase doc's scope).

## Fix
Added a `jupus_admin_token` cookie: the first request that presents a correct `?access_token=`
gets it set (`httponly`, `samesite=lax`) on the response, and the gate now accepts either the
query param or a matching cookie. Same-origin asset requests the browser fires afterward
automatically carry the cookie, so they pass without needing the query param repeated. Verified
via `TestClient`: `client.cookies` (the session-level jar, not a single response's `.cookies` —
the mount's own `/admin` → `/admin/` redirect is where the `Set-Cookie` actually lands) holds the
cookie after the first hit, and a bare `client.get("/admin/app.js")` with no query param succeeds.

## Verification
`pytest backend/tests/test_access_gate.py` (8 tests, including the new
`test_admin_asset_requests_pass_via_cookie_after_the_first_query_param_hit`) passes. Not yet
re-verified live against the Railway deployment — needs a redeploy first.
