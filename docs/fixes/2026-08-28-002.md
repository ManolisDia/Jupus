# Booking read the same three slots back twice when the caller counter-offered a different time

**Symptom**: On a real call (2026-08-28), after `suggest_alternative_slots` offered 9AM/9:30AM/10AM,
the caller said "Can you do Friday at 3 p.m.?" and got the *identical* previous reply back — "Sorry
Manos — that time at 4PM is already booked. I do have availability …". They then said "Sure, let's
just go with ten." and got the same message a **third** time. The 3PM request was never looked up.

**Root cause**, two independent defects that compounded:

1. `SELECT_OFFERED_SLOT_PROMPT` offered only three outcomes — picked one / declined all / didn't
   understand. A caller proposing a *different* time is none of those, so the model had nowhere to
   put it and returned `needs_clarification: true` (trace `#118`). `node_booking`'s clarification
   branch then replayed the previous agent reply verbatim via `_last_agent_reply`.
2. The prompt said slots could be picked "by time" or "by ordinal" but never covered a bare
   numeral. "Sure, let's just go with ten." also came back `needs_clarification` (trace `#128`).

The verbatim replay made both worse: repeating "that time at 4PM is already booked" is true once
and merely confusing after that, and it reads as the `repetition` error class to the eval judge.

**Fix**:
- `proposed_new_time` added to `SELECT_OFFERED_SLOT_SCHEMA` and the prompt as an explicit fourth
  outcome. `node_booking` routes it into `_handle_time_request()` — extracted from the existing
  `proposed_slot_id is None` branch so a counter-offer and a cold "what day works?" run the *same*
  lookup rather than two copies that drift.
- The prompt now covers bare numerals and affirmative-plus-reference ("sure, let's go with ten"),
  reserving ambiguity for numbers matching more than one option.
- The clarification re-ask uses a new deterministic `generate_offer_reprompt` (times only) instead
  of replaying the stale "already booked" preamble.

**Deliberate**: a counter-offer does **not** add the offered slots to `declined_slot_ids`. Asking
for 3PM is not refusing 9/9:30/10 — the caller in this very trace circled back to "let's go with
ten", which excluding them would have made impossible.

**Also deliberate**: the `LLMCallFailed` path inside `_handle_time_request` does not clear
`offered_slots`, unlike every other exit. The fallback asks the caller to repeat themselves, and a
repeated "let's go with ten" needs `select_offered_slot`, not `extract_datetime`. A failed turn must
not change which question the next turn is answering. This is pinned by
`test_counter_offer_llm_failure_keeps_the_offer_on_the_table` — the first draft of the fix got it
wrong (the early returns skipped the clearing step entirely) and a test caught it.
