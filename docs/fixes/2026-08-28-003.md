# `extract_datetime` hung ~10s and failed with an EMPTY error — adaptive thinking ate `max_tokens`

**Symptom**: On a real call (2026-08-28), mid-booking:

```
#101 tool_call_end  extract_datetime  duration_ms 10343  success false  error ""
#102 llm_retry      extract_datetime  attempt 1          error ""
#104 tool_call_end  extract_datetime  duration_ms 3952   success true
#105 llm_usage      extract_datetime  output_tokens 277
```

~14s of dead air on a voice call, and an error string that said nothing at all.

**Root cause**: `claude-sonnet-5` runs **adaptive thinking when the `thinking` parameter is
omitted** — omitting it opts *in*, not out. `call_claude_json` never passed it. On an utterance
the model found genuinely ambiguous ("can you do Friday at 4 p.m.?", asked *on* a Friday), the
thinking block consumed the entire `max_tokens=512` budget before any answer was emitted. The
response came back `stop_reason="max_tokens"` with content `['thinking']` and **no `text` block**.

`call_claude_json`'s `next(block.text for block in response.content if block.type == "text")` then
raised a bare `StopIteration` — whose `str()` is the **empty string**. That is the `error: ""` in
the trace, and it is why this was untraceable: `json.JSONDecodeError` and `anthropic.APIError` both
carry real messages, so an empty error could only ever have come from that one `next()`.

**Reproduced directly** against the API with the same utterance, prompt and `max_tokens`:

| thinking | result |
|---|---|
| omitted (current) | **2 of 3 runs FAILED** `stop_reason=max_tokens`, no text block; output 69–512 tokens; 3.0–6.3s |
| `{"type": "disabled"}` | **6 of 6 OK**; output a steady 32–36 tokens; 1.5–3.5s |

**Fix**:
- `NO_THINKING = {"type": "disabled"}` passed by `call_claude_json` and `call_claude_text`. Every
  call these make is a narrow extraction/classification against a small JSON schema on a
  latency-critical voice turn; none of them want a reasoning pass. `disabled` is accepted on both
  models these helpers run against (`claude-sonnet-5`, `claude-haiku-4-5`).
- `_first_text_block()` replaces the bare `next()` and raises `NoTextBlock` carrying
  `stop_reason`, `output_tokens` and the block types. It is in `RETRYABLE_ERRORS`, so behaviour is
  unchanged — but this class of failure can never again surface as `error: ""`.

**Behavioural change, deliberate — read this before assuming a regression.** Disabling thinking
changed an *answer*, not just latency: "Friday at 4pm" said on a Friday resolved to next Friday
with thinking on, and to *today* with it off. That reading was never stable — it depended on
whether that particular call happened to reason about it. `EXTRACT_DATETIME_PROMPT` now states the
rule outright (a bare weekday means the NEXT occurrence; today's weekday and that date are
interpolated in by `tools.extract_datetime`), which pins it in both directions: 6/6 correct across
"Friday" / "today" / "this afternoon" / "Thursday" / "tomorrow" / "next Monday".

**Not the same bug as `2026-08-25-002.md`**, despite the near-identical 10s-and-retry signature.
That one was a free-text schema field ballooning past `max_tokens`; this one is thinking tokens
consuming the budget before the answer starts. Same symptom, different mechanism, different fix —
and the earlier fix's "constrain the prompt, don't raise the cap" precedent still holds here:
`max_tokens` was left at 512, which is now ~15x what these calls actually use.

**Not yet validated by `eval/compare_runs.py`.** `extract_field`'s spoken-email conversions (the
behaviour that drove the Sonnet upgrade in `docs/DECISIONS.md`) were spot-checked and hold with
thinking off — `manos at gmail dot com` → `manos@gmail.com`, `manos dot d at outlook dot co dot uk`
→ `manos.d@outlook.co.uk` — but this touches shared plumbing used by every LLM-backed tool. A
labelled replay batch diffed against a baseline is the proper check, per the Phase 13 precedent.
