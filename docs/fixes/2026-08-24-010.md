# 2026-08-24-010 — Railway deploy: uvicorn unreachable, seed script `ModuleNotFoundError`

## Symptom
First Phase 9 Railway deploy: build succeeded (Railpack detected Python fine), but the container
crash-looped — `railway logs` showed `/bin/bash: line 1: uvicorn: command not found`, and the
public domain returned a 502 the whole time. After adding a `Procfile` pointing at
`python -m uvicorn ...` instead of the bare binary, the container itself came up, but the first
`railway ssh "python backend/db/seed_slots.py"` failed with `ModuleNotFoundError: No module named
'backend'` even though `backend/` (with `__init__.py`) was right there in `/app`.

## Root cause
Two separate issues, both about how the deployed environment resolves Python packages differently
from local dev:

1. **`uvicorn` not on `$PATH`.** This project only ships `pyproject.toml` (no `requirements.txt`).
   Railpack's Python provider detected the project as a Python/FastAPI app but — without an
   auto-detected start command (the app object lives at `backend.app:app`, not a root-level
   `app.py`/`main.py`, so Railpack's own FastAPI auto-start heuristic didn't fire) — the install it
   performed didn't reliably put `uvicorn`'s console-script entry point on the `$PATH` a custom
   `Procfile`'s `web:` command runs with. Same underlying failure mode showed up in two forms:
   `uvicorn` as a bare command wasn't found at all, and `python -m uvicorn` briefly reported "No
   module named uvicorn" (the `python` resolved on `$PATH` wasn't the same interpreter/environment
   pip had installed into).
2. **Bare script invocation vs. package resolution.** Same class of bug as
   [2026-08-21-005](2026-08-21-005.md): `python backend/db/seed_slots.py` puts `backend/db/` (the
   script's own directory) on `sys.path[0]`, not `/app` — so `from backend.config import settings`
   inside the script can't resolve `backend` as a package at all, deploy environment or not.

## Fix
- Added `requirements.txt` (pinned to the same version floors as `pyproject.toml`'s
  `dependencies`) — Railpack's Python provider has more reliable, better-tested support for
  `requirements.txt` than parsing `pyproject.toml`, and once picked up, it installs into an
  environment whose bin directory Railpack does put on `$PATH`.
- `Procfile`: `web: python -m uvicorn backend.app:app --host 0.0.0.0 --port $PORT` — `python -m`
  is kept even after fixing `$PATH`, since it's strictly more robust (resolves through whatever
  interpreter is actually running, rather than depending on a console-script shim being present).
- One-off commands against the deployed container (`railway ssh "..."`) must use module form, same
  as the local-dev convention `2026-08-21-005` already established:
  `python -m backend.db.seed_slots`, not `python backend/db/seed_slots.py`.

## Verification
Live: `railway ssh "python -m backend.db.seed_slots"` succeeded, seeding `/data/calendar.db` on
the mounted Volume. `curl -X POST .../session` (no token) returned 401 as expected; a real browser
call against the deployed Firebase client completed booking, escalation, and a low-confidence
capture turn end-to-end. A subsequent `railway redeploy` preserved the seeded slots and the one
call logged so far, confirming the Volume — not just the container's ephemeral disk — is what's
actually being read/written.
