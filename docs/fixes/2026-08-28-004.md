# 2026-08-28-004 — capture looped "could you spell out your email" forever: an optimistic retry, an uncounted attempt, and a discarded half of the answer

## Symptom
Live call. Caller gave a deliberately bad email ("Manos 44"), which was handled correctly — the
agent asked them to spell it out. From there it never recovered, alternating for the rest of the
call:

```
caller: "At gmail dot com."          agent: "Great — and what's your phone number?"
caller: <phone number>               agent: "…could you spell out your email address…"
caller: "At G M A I L dot C O M."    agent: "Great — and what's your phone number?"
caller: <phone number>               agent: "…could you spell out your email address…"
                                     -> call_abandoned
```

Two turns burned per attempt, no progress, and no escalation — the caller hung up. Trace events
#24–#80 of the captured call.

## Root cause
Three independent defects, each of which alone would only have degraded the call; together they
made it non-terminating.

**1. The fast path advanced optimistically on a *retry*.** `node_capture_fast`'s gate
(`heuristics.looks_like_field_shape`) is deliberately loose — "At gmail dot com." contains " dot ",
so it reads as an attempt at an email and the optimistic branch advanced to asking for the phone
number, leaving the real extraction to a background check (trace #40–#49). That is right for a
*first* answer, where guessing the caller got it right is usually correct and
`_verify_field_in_background` silently cleans up when it isn't. It is wrong for a retry: the field
had already failed once, so the guess was a bad bet, and losing it costs double — the caller hears
the conversation move forward ("Great — and what's your phone number?") and then jump backwards one
turn later, and `_delayed_failure_reask` deliberately discards the answer they gave in between.
Phase 7's design note reasoned about the cost of a wrong optimistic guess in general; it never
distinguished the first answer to a field from the second.

**2. A background verification failure was never counted as an attempt**, so the 3-strikes
escalation could not fire. `_verify_field_in_background`'s docstring explained this as deliberate —
"a background failure was never spoken to the caller, so it isn't a real attempt… the real attempt
only happens once the foreground actually re-processes this field for real, via node_capture_fast's
urgent-reask fallback (`_fallback_to_real_capture`), which reuses node_capture's existing attempts/
escalation logic." That urgent-reask fallback was removed in a later fix (see
`_delayed_failure_reask`'s own docstring: "an earlier version of this code did, via a since-removed
urgent-reask fallback") and the attempts bookkeeping was never moved across with it. The docstring
was left describing a mechanism that no longer existed, and `email["attempts"]` sat at 1 for the
rest of the call however many times it failed. This is also the unexplained half of
`docs/known-issues/2026-08-25-001.md` ("never reaching a 3-strikes escalation despite the repeated
failures").

**3. Each attempt was extracted in isolation, so a value split across two turns could never be
reassembled.** The caller's address is `manos44@gmail.com`. Attempt 1 delivered the local part
("Manos 44"), attempt 2 the domain ("At gmail dot com" → `@gmail.com`, trace #46). Both are
individually unusable and `validate_email` correctly rejected both, but together they are the whole
answer. Nothing carried the first half forward, so no number of retries could ever converge — the
loop was not just unbounded, it was unwinnable.

Note the two `speech_stopped` events preceding each of these turns (#37/#38, #58/#59): the caller
paused mid-spelling and the supervisor received only the tail segment. That is *not* a transport
bug to fix — `backend/transport/prompts.py` rule 3a explicitly forbids the realtime model from
merging consecutive utterances into one `ask_supervisor` call, a deliberate decision that prevents
a different class of misattribution. Given that, the halves can only ever be rejoined downstream,
which is what defect 3's fix does.

## Fix
**A retry is settled in the turn it arrives in** (`node_capture_fast`). A new branch, after the
tangent/shape gate and before the optimistic advance, catches
`attempts > 0 and status == "missing"` on `last_asked_field` and routes to `_finish_fast_pass` —
the existing "process this utterance against this field synchronously, with attempts/escalation
bookkeeping" operation. Traced as `capture_fast_retry_synchronous`. `_finish_fast_pass` gained a
`resume_field` branch so it can be called mid-pass: on success it resumes the fast pass on the next
never-asked field instead of dropping into the confirm/drain tail, which would have stranded those
fields unasked. That branch is structurally unreachable from the original end-of-pass caller, where
`asked_field` is `FIELD_PRIORITY`'s last entry.

**`_delayed_failure_reask` counts its attempt and escalates on the third**, with the shared
`CAPTURE_ESCALATION_REPLY`. A background check runs against an answer the caller really gave out
loud; the only thing "background" about it is where the work happened.
`_verify_field_in_background`'s stale docstring is corrected.

**A failed attempt's raw utterance is carried into the next one.** New `CallState` field
`partial_field_utterances`, written by `_remember_partial` on failure and dropped by
`_forget_partial` as soon as the field resolves (so a later re-ask after a denied confirm-back
starts clean). Scoped to `STITCHABLE_FIELDS = ("email", "phone")` — the only fields long enough to
get split across a pause, and the only ones with a deterministic validator to catch a bad stitch
before the caller hears it. `tools.extract_field` / `extract_and_confirm_field` take an optional
`previous_attempt`; `prompts.PREVIOUS_ATTEMPT_NOTE` is formatted into the prompt only when one is
present, so a first attempt sends a byte-identical prompt and makes a byte-identical call (asserted
by `test_first_attempt_prompt_and_call_are_unchanged`). The note deliberately *narrows* the
existing "never invent a domain / a missing @" guard rather than relaxing it — every character must
still come from something the caller actually said, but "what the caller said" now spans both
attempts — and defaults to using the new answer alone whenever the two don't clearly fit together.
Only the confirm-back-denial callers of `_deny_and_reprompt` skip recording a partial: a "yes",
"no", or correction is an utterance *about* a value, not a fragment *of* one.

## Verification
`pytest backend/tests eval/tests` — 416 pass (359 before, +6 new in `test_capture_fast.py`, all of
which fail on the pre-fix code), plus `scripts/check_architecture.py`. The new tests cover: the
retry being settled rather than advanced past; the previous attempt reaching `extract_field` and a
split address being rejoined; a first attempt's call being unchanged; a third synchronous failure
escalating; a third *background* failure escalating; and an end-to-end replay of the live call's
two derailing utterances through the real dispatcher, asserting it now advances to the phone
question with `manos44@gmail.com` captured. Not yet re-verified on a live call with a real mic.
