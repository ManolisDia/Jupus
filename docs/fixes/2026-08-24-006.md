# 2026-08-24-006 — `response.create` collision with an active response crashed the whole call

## Symptom
Live testing: mid-call, after saying something and then adding a follow-up a few seconds later
(no gap between utterances), the call abruptly ended. `client/app.js`'s data channel surfaced:

```
error: Conversation already has an active response in progress: resp_EGTscXZfNiEHRXerDrpAH.
Wait until the response is finished before creating a new one.
```

Trace confirmed the sequence: a supervisor reply was deferred (`reply_deferred`, `caller_speaking`),
then delivered ~3.75s later (`reply_delivered`, `wait_ms=3750`, `deferred=true`) right as the
caller's continued speech had already triggered its own auto-created response
(`turn_detection.create_response: true`). The deferred reply's own explicit `response.create`
(sent by `ws.onmessage`'s `supervisor_result` handler right after appending the tool's
`function_call_output`) then collided with that already-active response. The call ended in
`call_abandoned`.

## Root cause
Two compounding issues, both in `client/app.js`:
1. **The actual collision** — nothing checked whether a response was already active before
   sending `response.create`. Under the async dispatcher's design (`docs/DECISIONS.md`'s "async
   dispatcher defers/drops stale results" entry), a deferred reply landing right as the caller's
   own new utterance auto-creates a response is an *expected*, not exceptional, situation.
2. **The actual crash** — `dataChannel.onmessage`'s `type === "error"` handler unconditionally
   called `teardown(...)` for every Realtime API error, with no distinction between a genuinely
   fatal session error and a recoverable, expected-under-this-design rejection like this one. The
   API returning an `error` event for a redundant `response.create` does not itself end the
   session — the client's own overreaction did.

This is a related but distinct mechanism from `docs/known-issues/2026-08-22-001.md`'s original
symptom (an *in-flight* response getting cancelled by `interrupt_response` before it finishes
emitting a tool call) — that entry's "no client-side retry-on-cancel" position is unaffected by
this fix and remains the accepted residual limitation for that specific scenario. This fix is
about *our own* `response.create` call losing a race, not about a cancelled response.

## Fix
`client/app.js`:
- `requestResponse()` — the one path anything wanting the model to speak next now goes through
  (`ws.onmessage`'s `supervisor_result` handler calls it instead of sending `response.create`
  directly). Tracks `responseActive` (true between `response.created` and `response.done`); if a
  response is already active, sets `pendingResponseCreate = true` and returns instead of sending
  immediately. The `response.done` handler flushes at most one queued request once the active
  response actually finishes.
- This is deliberately *preventative* (checked before sending), not the *retry-after-cancel*
  mechanism the known-issues doc's "Failed workarounds" section already tried and reverted twice
  — it doesn't need per-response-ID tracking to decide whether to retry a specific cancelled
  response, only whether the response slot is currently claimed at all, so it isn't exposed to the
  event-ordering race that sank that earlier attempt.
- **The actual crash fix, and the one that matters even if the race above still occurs anyway**:
  the `error` handler now checks for `"already has an active response in progress"` in the error
  message and, if matched, logs a warning and returns — it no longer tears down the call. Every
  other error type still tears down as before. The `conversation.item.create` for the tool result
  always still succeeds (only `response.create` was ever rejected), so nothing is lost even when
  this backstop is what actually catches it — whichever response is genuinely active, or the next
  natural turn, ends up including it.
