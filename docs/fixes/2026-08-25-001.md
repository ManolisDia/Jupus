# 2026-08-25-001 — `ask_supervisor` could send the PREVIOUS turn's caller utterance, looping name/email capture forever

## Symptom
Live call: caller says why they're calling, agent correctly classifies it as immigration and asks for their name — but from there the call gets stuck cycling "what's your name" / "what's your email" / "sorry, what's your name again?" without ever actually recording either field. The admin transcript view also shows a caller line duplicated verbatim back-to-back, which turned out to be the same symptom, not a separate rendering bug.

Trace confirms it: `capture_fast_background`'s `extract_field(name)` call for the turn right after "what's your name?" was asked ran against `"Basically, they're trying to kick me out of the country."` — the caller's *original* statement from the turn before, not their actual answer ("Manos"). Confidence 0, so the background verification failed and `node_capture_fast` correctly re-asked the name — but every subsequent turn kept receiving the SAME one-turn-behind utterance, so the loop never broke on its own.

## Root cause
`client/app.js`'s `response.function_call_arguments.done` handler sends `ask_supervisor` using `lastVerbatimTranscript ?? args.last_caller_utterance` — `lastVerbatimTranscript` (the real ASR output from `conversation.item.input_audio_transcription.completed`) is deliberately preferred over the Realtime model's own `last_caller_utterance` argument, since the model has been observed "helpfully" inventing text the caller never said (see `docs/DECISIONS.md`).

That preference is correct, but the two events race and nothing enforced their order: `input_audio_transcription.completed` for the caller's latest utterance is not guaranteed to arrive before `response.function_call_arguments.done` for the same turn — ASR completion is asynchronous and can simply take longer than the model needs to decide to call `ask_supervisor`. When it lost the race, `lastVerbatimTranscript` still held whatever the *previous* turn had set it to, and that stale text got sent as `last_caller_utterance` with no signal anywhere that it was stale. `backend/dispatcher.py` and `backend/supervisor/graph.py` have no way to detect this — they trust the utterance they're given, per the architecture (deterministic graph edges, real ASR text as ground truth).

## Fix
`client/app.js` now tracks whether the current speech segment's transcription has actually landed:
- `transcriptionPending` is set `true` on `input_audio_buffer.speech_stopped` and cleared on the matching `conversation.item.input_audio_transcription.completed`.
- If `response.function_call_arguments.done` fires while `transcriptionPending` is still `true`, the `ask_supervisor` send is queued (`awaitingToolCall`) instead of firing immediately with a possibly-stale `lastVerbatimTranscript`.
- Once the real transcript arrives, the queued call is sent immediately with the fresh text.
- Both are reset in `teardown()` so nothing can leak into a later call.

`ws.send({type: "ask_supervisor", ...})` construction was factored into a small `sendAskSupervisor` helper since it's now called from two places (the immediate path and the queued-flush path).

## Known residual limitation, accepted rather than engineered around
If the ASR transcription event never arrives at all (a dropped event, not just a slow one), the queued `ask_supervisor` call would never fire and that turn would hang silently. No retry/timeout was added for this — `gpt-transcribe` completions failing to arrive at all (as opposed to arriving late) hasn't been observed in testing, and a timeout that falls back to the model's own (occasionally-hallucinating) argument would reintroduce the original bug this fix's preference for verbatim ASR was meant to close. Documented here rather than silently left unmentioned.
