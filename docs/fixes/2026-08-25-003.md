# LiveKit agent sat mute on every call — RoomIO silently drops audio tracks not published as `SOURCE_MICROPHONE`

**Symptom** (Phase 14, `docs/phases/phase-14-livekit-transport.md`): a LiveKit call connected
cleanly and looked correct from every angle — the worker registered with LiveKit Cloud, received
the job, joined the room, and published an audio track — but the agent never said anything and
`ask_supervisor` was never called. Zero `trace_events` rows for the call, no call record, no error
anywhere. Measuring the agent's published track from the caller side showed ~2000 audio frames
received with **zero** frames above the noise floor: a live, correctly-negotiated, permanently
silent track.

**What made it hard to localise**: everything upstream and downstream of the break looked healthy.

- The OpenAI Realtime connection was fine — proven by driving `RealtimeModel` standalone outside
  any LiveKit room, where it connected and returned `session.created` / `session.updated`
  immediately. (`LK_OPENAI_DEBUG=1` is required to see any of the plugin's connection logging; by
  default it logs nothing at all, which is why the connection initially looked like it never
  happened.)
- The caller's audio genuinely transmitted — proven with a two-participant loopback in a scratch
  room, where a plain subscriber received the synthesized speech with a healthy amplitude.
- RoomIO *did* find the track: instrumenting `_ParticipantInputStream` showed both
  `set_participant('caller')` and `_on_track_available(track kind=1 from caller)` firing.

So: audio transmits, RoomIO sees the track, the model is connected — and yet instrumenting
`RealtimeSession.push_audio` showed it was **never called once**.

**Root cause**: `livekit/agents/voice/room_io/_input.py`'s `_on_track_available` rejects a track
unless `publication.source in self._accepted_sources`, and for the audio input that set is
`{SOURCE_MICROPHONE}`. The test harness published the caller's track with
`publish_track(track)` and no options, so the publication's source defaulted to `SOURCE_UNKNOWN`.
`_on_track_available` therefore returned `False` and never started its forward task — so the
`AgentSession._forward_audio_task` had nothing to iterate, `AgentActivity.push_audio` was never
reached, and the Realtime model received no audio and had nothing to respond to. The rejection is
completely silent: no warning, no error, and `_on_track_available` still *runs* (which is why
instrumenting it was misleading — it fires and then returns `False` on the source check).

**The fix** is one argument on the publish call:

```python
await room.local_participant.publish_track(
    rtc.LocalAudioTrack.create_audio_track("caller-mic", source),
    rtc.TrackPublishOptions(source=rtc.TrackSource.SOURCE_MICROPHONE),
)
```

**Scope — this was never a product bug.** It only ever affected the synthetic-caller test harness
(`eval/livekit_live_call.py`). The browser client is unaffected: `livekit-client`'s
`setMicrophoneEnabled(true)` always tags the publication as `SOURCE_MICROPHONE`, so a real call
was never at risk. The bug was purely in code written to *test* the transport.

**What actually shortened the hunt**, worth reusing: running a **stock LiveKit agent** — the
framework quickstart, none of this project's code, same LiveKit project, same room — and watching
it fail in exactly the same way. That immediately ruled out every Jupus-specific design decision
(the in-process worker, `JobExecutorType.THREAD`, the cross-loop bridge, the single-tool schema,
the pre-rendered filler audio) in one step. Two hypotheses had already been chased and discarded
before that — an invalid Realtime model name (`gpt-realtime-2.1` probed fine directly against the
API) and a redundant `ctx.connect()` before `session.start()` (removing it made things strictly
worse: RoomIO then never linked the participant at all, and it was restored).

**Second, unrelated trap found in the same session** — worth knowing because it produced an
identically silent failure. LiveKit uses **automatic dispatch** when no `agent_name` is set, which
means *every* worker registered against the project is a candidate for *every* room. A leftover
stock-agent process from an earlier experiment kept winning the job, so the real worker logged
`registered worker` and then simply never received one — while the caller still saw "agent joined"
and assumed all was well. Because that other process has its own `CALL_STATES`, the call vanishes
from this process's admin panel and database with no error on either side. `start_agent_server()`
now logs a warning naming this failure mode at startup.
