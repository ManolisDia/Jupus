# 2026-08-21-004 — `python backend/db/seed_demo_calls.py` picked up code from a different checkout entirely

## Symptom
Working in the `phase-6a-observability` worktree (`.claude/worktrees/phase-6a-observability`),
running `python backend/db/seed_demo_calls.py` after adding the Phase 6c annotation tables failed
with `sqlite3.OperationalError: no such table: human_annotations` — even though `schema.sql` in
this worktree clearly defines that table and `reset_schema` had just been run via
`python backend/db/seed_slots.py` moments earlier in the same shell. A prior run in the same
session (before `sqlite_annotations.py` existed) had also failed with
`ModuleNotFoundError: No module named 'backend.db.repositories.sqlite_annotations'` despite that
exact file existing on disk in this worktree.

## Root cause
The `jupus` package is installed editable (`pip install -e ".[dev]"`), and that editable install's
`.pth`/finder metadata points at the **main checkout** (`C:\Users\Manol\PPP\Jupus`), not this
worktree — confirmed via `python -c "import backend; print(backend.__file__)"` printing the main
checkout's path from *inside* the worktree's directory.

`python backend/db/seed_demo_calls.py` (a bare file-path invocation) sets `sys.path[0]` to the
script's *own containing directory* (`backend/db/`), not the current working directory — so none
of that script's own `from backend.x import y` statements resolve against the worktree copy at
all; they fall through to the editable install and pull in the **main checkout's** `backend.config`,
`backend.db.repositories.connection` (whose `SCHEMA_PATH = Path(__file__).resolve().parents[1] /
"schema.sql"` then also resolves to the main checkout's older, table-missing `schema.sql`), etc.
The script file itself was read from the worktree (explains why the `ModuleNotFoundError` named a
module that very much exists in the worktree — the executing script was the new one, but its
imports weren't), while every module it imported came from wherever the editable install pointed.

`uvicorn backend.app:app` was NOT affected — uvicorn inserts the current working directory at
`sys.path[0]` before resolving the import string, so running it from inside the worktree correctly
picked up the worktree's `backend/app.py` and everything it imports. Neither was `pytest`, which
inserts `rootdir` ahead of site-packages for the directory pytest was invoked from.

## Fix
Invoke standalone scripts as modules from the repo root instead of by file path, so `sys.path[0]`
is `''` (the cwd) rather than the script's own directory:
```
python -m backend.db.seed_slots
python -m backend.db.seed_demo_calls
```
This makes the cwd (the worktree root, when your shell is `cd`'d into it) win over the editable
install's pointer for every `backend.*`/`eval.*` import inside the script. No code change was
needed — this is purely an invocation-style gotcha specific to working across multiple worktrees
of the same editable-installed package. Worth checking `python -c "import backend; print(backend.__file__)"`
first whenever a script run from inside a worktree behaves like it's reading stale code.
