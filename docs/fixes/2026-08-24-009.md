# 2026-08-24-009 — an unrelated earlier pending field could get silently "confirmed" by a mismatched utterance

## Symptom
Live testing: asked to spell out or confirm an email so it could be corrected/verified, the agent
never actually spoke a confirm-back question for it at all — it silently proceeded as if the email
had already been confirmed, using a genuinely wrong transcription the whole rest of the call
(`Manolediamandakis@gmail.com` instead of the caller's real address). Per `docs/DECISIONS.md`,
email/phone must *always* be read back and explicitly confirmed — this call never actually did
that for email.

## Root cause
Trace reconstruction: the caller answered the email question, which advanced the Phase 7 fast pass
to ask about phone while spawning a background verification of email (this succeeded,
confidence 0.85, merging email into `caller_profile` as `"pending_confirm"` — correctly, nothing
wrong yet). But right after being asked for their phone number, the caller repeated their email
again instead (a plausible human moment — replying before fully registering that a new question
had already been asked, worsened by the fast pass's own near-zero latency leaving no gap to
"catch up"). That utterance doesn't look like a phone number, so `node_capture_fast`'s shape gate
correctly fell back to the real, synchronous `node_capture`.

`node_capture`'s own `pending_field` lookup — `next(f for f in FIELD_PRIORITY if profile[f]["status"]
== "pending_confirm")` — picks the *first* pending field in `FIELD_PRIORITY` order with no
awareness of what was actually just asked about out loud. This is correct and safe during the
batched drain phase (`node_capture_confirm`), where fields are asked about strictly in that order,
so whatever's pending genuinely was just asked about. It is **not** safe when `node_capture` is
reached via `_fallback_to_real_capture` mid-fast-pass: Phase 7's background verification can mark
an *earlier* field `pending_confirm` well before its confirm-back has ever been spoken (that's
deliberately batched for later). Here, email was the only pending field, so it got picked up and
the caller's utterance was fed to `confirm_field_answer("...", "email", "manos@gmail.com")` — which
reasonably says "confirmed" since the caller's text *does* restate that email — silently marking it
confirmed without the caller ever having heard a confirm-back question, and completely discarding
whatever they actually meant to say about their phone number.

## Fix
`node_capture` (`backend/supervisor/graph.py`) gains an `allowed_pending_field: str = None`
parameter. `None` (the default, used by `node_capture_confirm`'s drain-phase call) keeps today's
"any pending field, in `FIELD_PRIORITY` order" behavior — safe there by construction.
`_fallback_to_real_capture` now passes `allowed_pending_field=state["last_asked_field"]` — when set,
`node_capture` only ever treats *that one field* as currently awaiting confirmation; any other
pending field is left completely untouched for this call, to be asked about for real later. With
this restriction, the same scenario now correctly falls through to a fresh (failed) extraction
attempt at "phone" instead — email stays `pending_confirm`, unconfirmed, exactly as it should.

## Verification
`pytest` (full suite, 296 tests) passes, including a new direct regression test
(`test_gate_fallback_does_not_confirm_an_unrelated_earlier_pending_field` in
`backend/tests/test_capture_fast.py`) reproducing this exact scenario. Not yet re-verified live —
needs a real call where a caller repeats an earlier field's value right after being asked about a
later one.
