# 2026-08-24-004 — Trace `seq` counter raced across threads and never survived a process restart

## Symptom
Found by a 6-agent codebase review (`docs/code-review-2026-08-24.md` findings #2 and #3), not
from a live symptom yet — caught before it corrupted a real call's trace ordering.

## Root cause
`SQLiteTraceRepository`'s `_seq_counters` was an in-memory `dict[str, int]` with a non-atomic
read-modify-write (`seq = self._seq_counters.get(call_id, 0); self._seq_counters[call_id] = seq + 1`).
`record_event` is called from both the `asyncio.to_thread` worker thread (via `GRAPH.invoke`'s
node functions) and the main event-loop thread (e.g. `drain_deferred`) for the *same* `call_id`
with no synchronization between them — once the `asyncio.to_thread` fix (`docs/fixes/` — see the
Phase 6 dispatcher fix) made real concurrent execution possible, two threads could read the same
`seq` before either wrote back, producing duplicate `(call_id, seq)` rows. `trace_events` only had
a non-unique index on that pair, so nothing caught it — `get_trace`'s `ORDER BY seq` would then
return an ambiguous/wrong event order. Separately, `_seq_counters` reset to empty on every process
restart, and the dev workflow runs `uvicorn --reload` (restarts on every file save), so a call in
flight across a restart got `seq=0,1,2…` again, colliding with its own pre-restart events.

## Fix
Removed the in-memory counter entirely. `record_event` now derives `seq` directly from
`SELECT COALESCE(MAX(seq), -1) + 1 FROM trace_events WHERE call_id = ?`, with the whole
read-then-insert wrapped in a `threading.Lock` so it's one atomic unit regardless of which thread
calls it. No cache to desync across threads or reset across a restart — it's always driven by
what's actually in the DB. Added a `UNIQUE` index on `(call_id, seq)` (was a plain index) as
defense in depth, so any future bypass of the lock fails loudly instead of silently corrupting
ordering.

Two regression tests in `backend/tests/test_tracing.py`: 20 real `threading.Thread`s hammering
`record_event` for the same `call_id` concurrently produce exactly `0..19` with no
duplicates/gaps; and a fresh `SQLiteTraceRepository` instance against the same connection
(simulating a restart — new Python object, same on-disk data) continues from the DB's real
`MAX(seq)` rather than resetting to 0.
