# 2026-08-24-007 — low-confidence email/phone silently skipped straight to a confirm-back that didn't reliably spell it out

## Symptom
Live testing: the agent asked "could you say that again?" a few times, with no indication of
*what* it needed. Separately, the user noted the agent spelled out their phone number back for
confirmation but not their email, on the same call — the confirm-back's spelling behavior felt
arbitrary.

## Root cause
`backend/supervisor/tools.CONFIRM_BACK_PROMPT` instructs Claude to "spell out ambiguous characters
if it would help the caller confirm accurately" — a soft, discretionary instruction, and the sole
mechanism `generate_confirm_back` had for surfacing extraction uncertainty to the caller. Nothing
about a *low-confidence* email/phone extraction ever reached this decision differently from a
high-confidence one: `node_capture`, `node_capture_fast`'s `_finish_fast_pass`, and
`dispatcher._verify_field_in_background` all sent any non-empty, correctly-*formatted* email/phone
value straight to `pending_confirm` regardless of how low the extraction confidence actually was —
confidence was computed but never checked for these two fields (unlike `apply_extraction`'s
0.4/0.75 thresholds for name/preferred_time). A low-confidence-but-well-formed value (e.g.
Claude unsure it transcribed a mumbled email correctly, but the shape still looked plausible) then
relied entirely on Claude choosing, turn to turn, whether spelling it out "would help" — which
this live session showed isn't reliable.

## Fix
`backend/supervisor/graph.py` adds `LOW_CONFIDENCE_CONFIRM_THRESHOLD = 0.75` (the same bar
`apply_extraction` already treats as "confident" elsewhere) and `SPELL_OUT_REPLIES` (a fixed,
deterministic reply per field — never left to Claude's discretion, same lesson as the
Haiku→Sonnet entry in `docs/DECISIONS.md`). Below that threshold, email/phone extraction is now
treated exactly the same as an *invalid format* — re-asked immediately, not sent to
`pending_confirm`/a confirm-back at all:
- `node_capture`'s fresh-extraction branch checks confidence right after the format check.
- `_finish_fast_pass` (the live, last-field path) checks confidence alongside its existing
  format/validator check.
- `dispatcher._verify_field_in_background` (the background-verification path — the *common* case
  under Phase 7's optimistic capture, since most fields are asked about before their real
  extraction has even started) now also fails on low confidence, not just invalid format. This
  routes it through the existing delayed-failure interrupt-and-reask mechanism
  (`_delayed_failure_reask`), which now gives email/phone the same spell-out message.

Because the gate is enforced at every point a field can reach `pending_confirm`, by construction
any field that *does* reach the confirm-back step already cleared the confidence floor — so the
existing Claude-generated `generate_confirm_back` call (and its soft spelling instruction) never
needed to change; it's now only ever invoked on values already known to be confidently heard.

`docs/DECISIONS.md`'s "email/phone are always confirmed back regardless of confidence" entry is
refined (not reversed) with this nuance — still true once confidence clears the floor.
`docs/scenarios.md`'s S4 updated to exercise the new low-confidence-reask-then-succeed path.

## Verification
`pytest` (full suite, 280 tests) passes, including a new direct test
(`test_low_confidence_well_formed_email_asks_to_spell_out_instead_of_confirming`) and a
restructured S4 scenario covering the reask-then-spell-out-succeeds flow end to end through the
real dispatcher. Not yet re-verified live with a real mumbled/low-confidence email on an actual
call.
