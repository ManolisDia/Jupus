# 2026-08-21-004 — Deferred reply dropped as "stale" by the very turn that produced it

## Symptom
Discovered while writing a `/bridge` integration test for the Phase 5 async dispatcher: a
`speech_started` → `ask_supervisor` (greeting) → `speech_stopped` sequence hung forever waiting
for the `supervisor_result` reply — it never arrived, and no error was logged.

## Root cause
`process_supervisor_call` tagged each deferred reply with `dispatch_stage = state["stage"]`
captured **before** `GRAPH.invoke(...)`, per the phase 5 doc's literal pseudocode
(`docs/phases/phase-5-escalation-async.md`). Any node that naturally advances the stage as part
of producing its own reply (e.g. `node_greeting`: `greeting` -> `routing`) causes
`drain_deferred`'s staleness check (`dispatch_stage != current_stage`) to compare the turn's own
*pre*-invoke stage against its own *post*-invoke stage — a guaranteed, false-positive mismatch
that silently drops the reply on every single-turn stage transition while the caller was mid-speech
at delivery time. The two staleness tests in the phase doc didn't catch this because they inject
data directly into `DEFERRED`/`CALL_STATES` rather than exercising the real `process_supervisor_call`
path.

## Fix
Tag the deferred reply with the **post-invoke** stage (`dispatch_stage = updated["stage"]`)
instead — the stage this reply's content is actually about. Staleness now only fires when a
*separately dispatched, later* turn has moved the conversation further by the time this one is
drained, which is what the check is actually meant to catch. Added
`test_bridge_relays_speech_started_and_stopped` in `backend/tests/test_bridge_endpoint.py`, which
exercises the real WS -> dispatcher -> graph -> deferred-delivery path end to end (the existing
`test_dispatcher_async.py` staleness tests still pass since they don't exercise this code path).
